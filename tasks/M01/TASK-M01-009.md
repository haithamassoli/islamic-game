## Objective
`DecisionLog` ينفذ خط FR-E4 كاملاً بشكل متزامن: بناء الحدث وإعطاؤه `seq`، ثم الشهود، ثم الاقتصاد، ثم التسجيل غير القابل للتعديل، ثم قائمة معالجات المحاكاة الثابتة الترتيب، ثم `OnRecorded` للعرض فقط، مع طابور متابعة يمنع التداخل.

## Description
[PRD 7.1](../../docs/PRD.md) FR-E1..FR-E4 و[PRD 8.2](../../docs/PRD.md) و[D-004](../../planning/DECISIONS.md): الترتيب جزء من الصحة، فلا message bus ولا اشتراك بترتيب التسجيل. ترتيب المعالجات ثابت في الكود: الذاكرة والمعتقدات ← السجل الأخلاقي ← التوبة ← العلاقات والسمعة ← الجدولة ← حالة القصة. لا يُحفظ في منتصف الخط (FR-S3). المعالجات الفعلية تأتي في M05 وM07 وM12؛ هنا الخط والعقد والاختبارات بمعالجات تجسس.

## Implementation Plan
1. `public interface ISimulationHandler { string HandlerId { get; } long LastProcessedSeq { get; set; } void Handle(GameEvent e); }` (الواجهة المسموحة الثالثة في PRD 8.2). منطق `LastProcessedSeq` يُكمل في [TASK-M01-010](TASK-M01-010.md).
2. `HandlerOrder`: مصفوفة ثابتة بالمعرفات `memory, moral, repentance, social, scheduling, story`. مُنشئ `DecisionLog` يرفض قائمة معالجات خارج هذا الترتيب النسبي أو بمعرف مكرر أو مجهول (يسمح بمجموعة جزئية مرتبة لأن المعالجات تُبنى تدريجياً).
3. خطوات خارجية بلا واجهات: `DecisionLog` يستقبل في مُنشئه `Action<GameEventDraft> computeWitnesses` و`Action<GameEventDraft> applyEconomy` (افتراضياً لا شيء)؛ يمررها `SimulationWorld` كـ method groups من `Perception` ([TASK-M05-001](../M05/TASK-M05-001.md)) و`EconomyLedger` (M04). استدعاء مباشر لا ناقل.
4. `long Submit(GameEventDraft draft)`:
   - إن كان `IsProcessing` ← يُضاف لطابور متابعة FIFO ويُرجَع `-1` (الرقم يُعطى عند المعالجة).
   - وإلا: `IsProcessing=true`، ثم حلقة: (1) `seq = NextSeq++`، وملء `Day/Time` من `GameClock` إن لم تُحدد؛ (2) الشهود؛ (3) الاقتصاد؛ (4) `Freeze` ثم `GameEventValidator` ثم الإلحاق بـ `events`؛ (5) المعالجات بالترتيب؛ (6) `OnRecorded`؛ ثم سحب التالي من طابور المتابعة حتى يفرغ؛ ثم `IsProcessing=false`.
5. `event Action<GameEvent> OnRecorded`: يُستدعى كل مشترك داخل try/catch؛ استثناء العرض يُبلَّغ عبر `Action<Exception> OnPresentationError` ولا يوقف المحاكاة. استثناء معالج محاكاة يُعاد رميه (حالة غير متسقة = خطأ برمجي).
6. قراءة: `IReadOnlyList<GameEvent> Events`، `bool TryGet(long seq, out GameEvent e)`، `long NextSeq`، `bool IsProcessing`، `bool IsAtSafePoint => !IsProcessing`.
7. الحالة: `DecisionLogState { long nextSeq; List<GameEvent> events }` مع `ToState()`/`FromState()`؛ الاستعادة لا تستدعي معالجاً ولا `OnRecorded` (FR-S2).
8. توثيق التواقيع ومخطط التسلسل في [docs/systems/EVENT_PIPELINE.md](../../docs/systems/EVENT_PIPELINE.md).

## Acceptance Criteria
- [ ] 1000 حدث متتالٍ تأخذ `seq` من 1 إلى 1000 بلا فجوة أو تكرار.
- [ ] ستة معالجات تجسس تُستدعى بترتيب `HandlerOrder` لكل حدث (سجل الاستدعاء يطابق حرفياً)، و`OnRecorded` بعد آخرها.
- [ ] قائمة معالجات بترتيب خاطئ أو معرف مكرر ترمي في المُنشئ.
- [ ] `Submit` من داخل معالج لا يتداخل: الحدث الجديد يُعالج بعد انتهاء الحالي بكل خطواته، بترتيب FIFO.
- [ ] `IsAtSafePoint=false` داخل أي معالج أو مشترك `OnRecorded`.
- [ ] مشترك `OnRecorded` يرمي استثناءً لا يغيّر `Events` ولا `NextSeq` ولا يمنع الحدث التالي.
- [ ] نفس سيناريو الأحداث مع مشتركين في `OnRecorded` وبدونهم يعطي `ToState()` متطابقاً حقلاً بحقل.
- [ ] `FromState` لا يستدعي أي معالج أو مشترك.

## Potential Issues
- معالج يقرأ حالة معالج لاحق في الترتيب يرى قيمة قديمة: موثق؛ القراءة تكون فقط لما سبق في الترتيب.
- حلقة متابعة لا تنتهي (معالج يصدر حدثاً كل مرة): حد أقصى (مثلاً 64 حدث متابعة لكل `Submit`) يرمي في نسخ التطوير.
- المشترك في `OnRecorded` يحتفظ بمرجع لحالة قابلة للتغيير: لا يُمرر له إلا `GameEvent` غير القابل للتعديل.
